# ADR 0002: Enforce the Content-Security-Policy with a per-request nonce

- Status: accepted
- Date: 2026-11-12

## Context

The policy shipped report-only, with `script-src 'self' 'unsafe-inline'`:
an injected inline script would still have run, so it protected against
little beyond framing and plugins. The known violation, Zod's `new
Function` probe, is gone (Zod runs jitless, `src/instrumentation-client.ts`).
The next step was to enforce it, with something narrower than
`'unsafe-inline'` for scripts.

What a page needs (checked by loading every page in Chromium against the
built Worker in workerd, signed out and signed in, with the policy
enforced):

- **Scripts.** Next.js renders `<script src="/_next/static/...">` tags and
  inline scripts that carry the RSC payload (`self.__next_f.push(...)`),
  which differ on every response. The root layout adds two inline scripts
  of its own: Mantine's `ColorSchemeScript` and the scroll-reveal flag.
  Next.js chunks load further chunks at runtime, and PostHog loads its
  remote config and extensions (replay recorder, exception autocapture,
  dead clicks) as script elements from `/lens/static/...`. Nothing uses
  `eval`. Stripe Checkout is a redirect (no Stripe.js); Google Places is
  called by the server through tRPC (no Maps script).
- **Styles.** Mantine writes `style` attributes everywhere and injects
  `<style>` elements at runtime.
- **Connections.** Same origin only: tRPC, `/lens` (PostHog through the
  app's own origin), and the realtime WebSocket to the app's own host.
- **Images.** Same origin, `data:`/`blob:`, Cloudinary, Google avatars.

## Options

1. **Hashes of the inline scripts** (`'sha256-…'`). The RSC payload scripts
   change with every response, so their hashes cannot be known in advance.
   Next.js's `experimental.sri` covers external chunks only. Not workable
   without `'unsafe-inline'`.
2. **A nonce stamped by the Worker entry** (`HTMLRewriter` adding a nonce to
   every `<script>` in every HTML response). Works for any page, cached or
   not, but it trusts *every* script element in the markup, including one
   an attacker managed to inject, which is exactly what a nonce is meant to
   tell apart.
3. **Next.js's own nonce support.** The middleware makes a nonce, puts the
   policy in the *request* headers, and Next.js adds the nonce to every
   script it renders (it reads `'nonce-…'` from the request's
   `content-security-policy` header). The app's own inline scripts take it
   from the request headers too. The cost Next.js documents: a page with a nonce must be
   rendered per request, never served prerendered.

## Decision

Option 3, with `script-src 'self' 'nonce-…' 'strict-dynamic'`:

- **It costs no caching here.** The root layout reads the session
  (`auth()`), so every page was already dynamic before this change: the
  build lists every page as `ƒ (Dynamic)`; only `robots.txt` and
  `sitemap.xml` are static, and they carry no scripts.
- **It works on OpenNext.** On the built Worker (`wrangler dev`, workerd)
  every page came back with the policy and every `<script>` and
  `<link rel="preload" as="script">` carrying that response's nonce; a new
  nonce per response; zero violations across all pages (list below).
- **Only scripts the app emits run.** An inline `<script>` added to the
  markup without the nonce is blocked (the E2E test does exactly this).
  `'strict-dynamic'` lets nonced scripts load what they need (Next.js
  chunks, PostHog's extensions) without listing hosts; `'self'` is only for
  browsers that predate `'strict-dynamic'` and is ignored by the rest.
- **The mode is a runtime switch.** The middleware reads `CSP_MODE`
  (`enforce`, the default, or `report-only`). Changing the variable makes
  Cloudflare roll out a new Worker version within seconds, so the policy can
  be relaxed to report-only without a code deploy (docs/DEPLOYMENT.md). The
  value is trimmed and lower-cased; anything unrecognised enforces, so a typo
  can neither switch the policy off nor fail environment validation and take
  the site down. Both modes report to `/api/csp-report`.
- **Responses without a page policy still get one.** API routes, `/_next/*`
  and `/img/*` skip the middleware, but Next.js can render the HTML
  not-found page for an unknown path there. They are given a static
  `default-src 'none'; frame-ancestors 'none'; base-uri 'none'`, which also
  hardens JSON responses. The Stripe webhook (`/webhooks/*`) skips the
  middleware so nothing sits in front of its signature check.

`style-src` keeps `'unsafe-inline'`. Mantine depends on `style` attributes,
which cannot carry a nonce (only `'unsafe-hashes'` with a hash per distinct
value could allow them), and a nonce in `style-src` would make browsers
ignore `'unsafe-inline'` and block those attributes. Styles cannot run
script; the residual risk is CSS-based data exfiltration from an injected
`<style>`, which `default-src`, `img-src` and `connect-src` limit to the
hosts listed.

The policy is set by the middleware (`src/middleware.ts`, which now runs on
every page; `/app/*` still requires a session) through
`src/_lib/contentSecurityPolicy.ts`, and built by
`buildContentSecurityPolicy` in `src/securityHeaders.js`. `next.config.js`
no longer sets it: a static header could not carry the nonce, and two
policies would both apply. API routes, `/_next/*` assets and files in
`public/` get no policy (they render no HTML); they keep the other headers,
including `X-Frame-Options: DENY`.

## Pages checked

Signed out: `/`, `/login`, `/join`, `/register` (redirects to `/join`),
`/waitlist`, `/about`, `/privacy`, `/terms`, `/contact`,
`/photographer/<handle>` (existing and unknown, 404), an unknown page (404),
`/app/events` (redirect to `/login`), and a client-side navigation.

Signed in: `/app/events` (and the Create event dialog, with the location
field typed into), `/app/events/<id>` (existing and unknown),
`/app/bookings`, `/app/messages`, `/app/messages/<thread>` (sending a
message over the realtime WebSocket), `/app/search` (with a query),
`/app/discover`, `/app/discover/matches`, `/app/profile`,
`/app/photographer/<id>` (own and another member), `/app/settings`,
`/app/notifications`, `/app/invites`, `/app/onboarding`,
`/app/admin/waitlist`, `/photographer/<own handle>`, an unknown `/app` page
(404), and client-side navigation between tabs.

Also with a build that has a PostHog token and analytics consent granted,
against a local stand-in for PostHog's hosts serving the real `posthog-js`
extension files: the SDK started, loaded its exception-autocapture extension
through `/lens/static/...` on every page and sent events, without a
violation. The session replay recorder is loaded the same way (a script
element the SDK inserts, which `'strict-dynamic'` allows); it was not
triggered locally because the stand-in's remote config is never requested.

Note what `'strict-dynamic'` means: a script element created with
`document.createElement` and inserted by running code is allowed, nonce or
not. The nonce stops markup injection (a `<script>` or an `on*=` attribute
in the HTML), not a script the app's own code chooses to insert.

## Consequences

- A new inline `<script>` must take the nonce: in a server component read
  it with `await requestNonce()` (`~/_lib/requestNonce`); `next/script` gets it from
  Next.js. A third-party script host would need a source in the policy (and
  is ruled out anyway: telemetry is first-party).
- Every page request runs the middleware (one random nonce, one header);
  `/app/*` also decodes the session there, as before.
- `e2e/csp.spec.ts` fails on any violation on the key pages, so a change
  that breaks the policy fails CI before it reaches production.
- If the policy breaks something in production anyway: set
  `CSP_MODE=report-only`, read the `csp_violation` events, fix, and remove
  the variable.
